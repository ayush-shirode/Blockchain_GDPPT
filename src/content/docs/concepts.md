# Core Concepts

This guide introduces the foundational concepts of Self-Sovereign Identity (SSI), Decentralized Identifiers (DIDs), and Verifiable Credentials (VCs). Each section begins with a plain-English explanation before defining technical standards.

---

## 1. The Trust Triangle: Three Roles

In traditional identity systems, third-party identity providers (e.g. Google, national central logins) must be contacted every time you authenticate. If that central provider goes down or revokes your account, you lose access everywhere.

In Self-Sovereign Identity, identity interactions form a three-party **Trust Triangle**:

```
           [ 1. ISSUER ] (Government Authority / University)
             /       \
 (Signs VC) /         \ (Publishes DID & Revocation Digests)
           v           v
    [ 2. HOLDER ] ---> [ 3. VERIFIER ] (Hospital / Bank)
     (Citizen)   (Presents Disclosed Claims)
```

1. **The Issuer (Authority)**:
   - *Plain English*: The trusted entity that issues a credential (e.g., Municipal Corporation, State University, Tax Department).
   - *Technical*: Holds an asymmetric cryptographic key pair, maintains an active DID in the Trust Registry, signs digital credentials using Ed25519, and posts revocation states to the ledger.
2. **The Holder (Citizen)**:
   - *Plain English*: The person who owns and controls the credential.
   - *Technical*: Stores the issued VC in an off-chain digital wallet, decrypts it locally, and generates cryptographically signed Verifiable Presentations (VPs) disclosing only the required fields.
3. **The Verifier (Relying Party)**:
   - *Plain English*: The organization requesting proof of your qualifications or identity (e.g., an employer, hospital, or bank).
   - *Technical*: Evaluates the presentation without contacting the issuer directly. The verifier uses public cryptographic keys and ledger status registries to confirm authenticity.

## 2. Decentralized Identifiers (DIDs)

### Plain English
A DID is a globally unique digital identifier that does not depend on a central domain registrar (like `.com`) or email provider. You control it through your own cryptographic keys.

### Standard Definition (W3C DID v1.0)
A URI formatted according to the syntax:
```
did:<method>:<method-specific-id>
```
In this demonstration portal:
- Issuers and citizens use the **`did:key`** method:
  `did:key:z6MkuTjN9z...`
- The `did:key` representation deterministically derives from an Ed25519 public key using multicodec prefixing (`0xed01`) and base58-btc encoding.
- Because the public key is embedded in the identifier string itself, resolution does not require a network round-trip, making offline verification possible.

## 3. Verifiable Credentials (VCs)

### Plain English
A Verifiable Credential is the digital equivalent of a physical document (such as a passport, degree, or driver&apos;s license) that is cryptographically tamper-proof. If anyone alters even a single character, the digital signature becomes invalid.

### Technical Structure (W3C VC Data Model)
A VC comprises:
1. **Metadata**: Context URI (`@context`), credential type (`type`), issuance date (`issuanceDate`), expiration date (`expirationDate`).
2. **Issuer Identifier**: The issuer&apos;s DID (`issuer`).
3. **Subject Claims**: Attributes describing the holder (`credentialSubject`), such as name, date of birth, license class, or university degree.
4. **Proof / Signature**: A cryptographic signature generated by the issuer using their private key.

In this portal, credentials are packaged as **VC-JWT** tokens conforming to RFC 7519 and W3C VC specifications, signed with Ed25519 (`EdDSA`).

## 4. Selective Disclosure (Salted-Hash / SD-JWT)

### Plain English
When showing a physical driver&apos;s license to enter an age-restricted venue, the bouncer sees your full name, home address, and license number. With **selective disclosure**, you reveal only the attribute that matters (e.g., *Is Age ≥ 18?* or your date of birth) without exposing your home address.

### Technical Implementation
To maintain absolute technical precision, this system implements **Salted-Hash Selective Disclosure (SD-JWT pattern)**:
1. When issuing the credential, the issuer calculates an independent cryptographic hash for each claim using a unique random cryptographic salt:
   $$\text{digest}_i = \text{SHA-256}(\text{salt}_i \parallel \text{attributeName} \parallel \text{attributeValue})$$
2. The issuer signs the list of digests in the master VC-JWT payload.
3. When creating a proof presentation, the citizen selects which claims to reveal. For unrevealed claims, only the raw hash is passed. For revealed claims, the citizen provides the attribute value and its salt.
4. The verifier recomputes the SHA-256 digest of the revealed claims and matches them against the issuer&apos;s signed array of digests.
5. **Important Notice**: This mechanism is **salted-hash disclosure**, *not* zero-knowledge cryptography. It is never labeled "zero-knowledge."

## 5. Credential Revocation

### Plain English
If a license is suspended, a degree is rescinded, or a credential was issued in error, the issuer must have a way to cancel it without tracking when or where the citizen uses it.

### Ledger-Based Revocation Status
1. The issuer publishes a revocation record to the distributed ledger:
   ```json
   {
     "eventType": "CREDENTIAL_REVOKED",
     "credentialId": "cred-uuid-1234",
     "revocationReason": "DOCUMENT_SUPERSEDED",
     "issuerDid": "did:key:z6Mku...",
     "timestamp": 1729900000000
   }
   ```
2. During verification, the relying party queries the ledger adapter for the status of `credentialId`.
3. If a revocation event exists on-chain, the verification pipeline immediately halts with the outcome **Revoked**.
4. The issuer cannot learn who is verifying the credential or why; they only publish the revocation digest.
